01 / CONCEPT

Zero Trust دقیقاً چه می‌گوید؟

اصل ساده: صرف اینکه یک کاربر، سرویس یا دستگاه «داخل شبکه» است، نباید باعث شود به آن اعتماد ضمنی کنیم. NIST در معماری Zero Trust تمرکز را از محیط شبکه به منابع، هویت‌ها و سیاست‌های دسترسی منتقل می‌کند.

Never Trust

موقعیت شبکه به‌تنهایی مدرک اعتماد نیست. یک سرویس داخلی هم باید هنگام درخواست دسترسی قابل شناسایی و ارزیابی باشد.

Verify Explicitly

هویت و شرایط دسترسی قبل از اعطای دسترسی بررسی می‌شوند؛ احراز هویت و مجوزدهی دو مفهوم جدا هستند.

Protect Resources

هدف نهایی فقط «محافظت از شبکه» نیست؛ API، سرویس، دیتابیس و داده خودِ منابعی هستند که باید محافظت شوند.

02 / SERVICE IDENTITY

وقتی سرویس‌ها هم هویت دارند

در معماری Microservices، فقط انسان‌ها نیستند که درخواست ارسال می‌کنند. سرویس A ممکن است به سرویس B درخواست بدهد و این ارتباط باید قابل شناسایی و سیاست‌گذاری باشد.

03 / ACCESS CONTROL

Least Privilege؛ فقط همان‌قدر که لازم است

اگر یک سرویس فقط باید سفارش‌ها را بخواند، چرا باید بتواند جدول کاربران را حذف کند؟ کمینه‌سازی مجوز، دامنه‌ی آسیب یک حساب یا سرویس compromised شده را کاهش می‌دهد.

-- Bad idea GRANT ALL PRIVILEGES ON *.* TO 'orders'; -- Better direction GRANT SELECT ON shop.orders TO 'orders'; -- حتی بهتر: مجوز را بر اساس نیاز واقعی و سیاست محیط محدود کن.
نکته: Least Privilege یک «دستور SQL» نیست؛ یک اصل طراحی است که باید از API تا سرویس و تا دیتابیس دنبال شود.
04 / API SECURITY

API؛ دروازه‌ای که نباید فقط قفل داشته باشد

APIها منطق برنامه و داده‌های حساس را در معرض درخواست قرار می‌دهند. در OWASP API Security Top 10، مشکلات Authorization جایگاه مهمی دارند.

Object-Level Authorization

داشتن یک توکن معتبر به این معنی نیست که کاربر باید بتواند هر object ID را بخواند.

Broken Authentication

احراز هویت ناقص می‌تواند هویت درخواست‌کننده را قابل سوءاستفاده کند.

Resource Consumption

Rate limiting و کنترل مصرف منابع در برابر درخواست‌های بیش از حد اهمیت پیدا می‌کند.

SSRF

یک API که URL دریافتی را بدون کنترل به مقصدهای داخلی می‌فرستد، می‌تواند سطح حمله ایجاد کند.

Security Misconfiguration

تنظیمات ناامن، endpointهای debug و پیکربندی‌های اضافی می‌توانند مسیر حمله بسازند.

Inventory

اگر ندانیم چه endpointها و نسخه‌هایی فعال‌اند، نمی‌توانیم به‌درستی از آن‌ها محافظت کنیم.

05 / DATABASE

یک معماری امن نباید بعد از API متوقف شود. حتی اگر درخواست از یک سرویس معتبر آمده باشد، دسترسی دیتابیس باید محدود، قابل حسابرسی و متناسب با نیاز باشد.

06 / CLOUD NATIVE

Microservices و Cloud؛ جایی که Zero Trust جدی‌تر می‌شود

در محیط‌های Cloud و Microservices، مرز شبکه مثل گذشته ثابت نیست. NIST در SP 800-207A نیز بر هویت‌های application و service در کنار هویت کاربر تأکید می‌کند.

Service → Service

ارتباط داخلی هم باید هویت و سیاست داشته باشد؛ «داخل VPC بودن» به‌تنهایی کافی نیست.

Policy as Code

بخشی از سیاست‌های دسترسی را می‌توان به شکل قابل بررسی و تکرارپذیر در چرخه توسعه وارد کرد.

Observe & Audit

دسترسی را فقط مجاز یا رد نکن؛ ثبت رویدادها برای فهم رفتار سیستم و بررسی رخدادها مهم است.

11 / GLOSSARY

واژه‌نامه سریع

Zero Trust

مدلی که اعتماد ضمنی را حذف و دسترسی را بر اساس هویت و سیاست بررسی می‌کند.

Least Privilege

اعطای حداقل سطح دسترسی موردنیاز برای انجام یک وظیفه.

Workload Identity

هویت قابل استفاده برای یک workload یا سرویس در محیط‌های Cloud Native.

RBAC

کنترل دسترسی مبتنی بر نقش؛ مجوزها از طریق roleها مدیریت می‌شوند.

mTLS

احراز هویت دوطرفه TLS که در آن هر دو سمت ارتباط هویت خود را ارائه می‌کنند.

Audit Log

ثبت رویدادهای مهم برای بررسی، تشخیص و پاسخ به رخدادهای امنیتی.
